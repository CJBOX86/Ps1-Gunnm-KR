## 폰트 처리 (실행 추적 근거)
- KNJ 개수 = `0000` 종료 전까지 (`0x80027C94`). 초기화 `0x800279B8(KNJ, …)`
- KNJ 버퍼 0x8013E000 뒤로 약 4KB 비어 있음 → 상한 1,444자(2,890byte)도 들어감
- 방식: 한글 음절마다 어떤 KNJ에도 없는 JIS 한자 코드를 하나 배정(모든 폰트 공통) → 블록의 `font_candidates` 폰트마다 KNJ에 추가·정렬 → TIM 재배치(높이 갱신)
  - 1,444자를 넘으면 대사·메뉴 휴리스틱 집합이 안 쓰는 일본어 글자부터 뺀다. 그래도 넘으면 빌드 실패
  - 옮긴 원래 글리프는 픽셀 단위 자가 검사
- 처음에 시도한 "안 쓰게 된 일본어 슬롯 재활용"은 부분 번역 상태에서 빈 슬롯이 없어 폐기

## 개발 중 고친 결함 (재발 방지 검사 포함)
1. KNJ 끝의 `0000` 종료를 글자로 취급 → 정렬 후 맨 앞에 와서 글자 수 0 → 타이틀 글자 깨짐. 종료 앞까지만 읽도록 수정
2. 4bpp 니블 선택을 칸 안 x로 계산 → 홀수 시작 칸으로 옮긴 글리프가 깨짐(`最`). 절대 x로 수정, 빌드에 글리프 이동 자가 검사 추가
3. 번역문 한 줄이 25칸 초과 → 글자 단위 자동 줄바꿈. 빌드 경고 추가

## 한계·남은 일
- `font_candidates`는 글자 집합 추정이라 한글이 여러 폰트에 중복으로 들어간다 (장면↔폰트 실제 매핑 조사 필요)
- 메뉴 보호 글자 집합은 휴리스틱 (NOR/*.E·실행 파일의 SJIS 연속열)
- 띄어쓰기가 전각 폭이라 넓다 → 반각 공백 글리프·폭 처리 검토 필요
- 개발용 글꼴은 Windows 굴림 12px — 배포 글꼴 결정 필요
- LDP가 아닌 2개 파일(`DATA/STS_0.SPB`, `M5/L/MP999_0.EDP`)은 크기 증가 미지원
- 번역 줄 0개일 때는 아무 파일도 바꾸지 않음 (확인)
